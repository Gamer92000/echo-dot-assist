# Получение root на Mi Smart Speaker L09G с Марусей

Эта заметка описывает опыт владельца одной колонки и дополняет, а не заменяет [статью автора SpeakerLab](https://habr.com/ru/articles/1107780/) и документацию внутри архива SpeakerLab 1.0. Метод относится к российской версии с Марусей; глобальную версию с Google Assistant SpeakerLab 1.0 не поддерживает. Root нужен до установки порта; готового установщика порта для чистой колонки пока нет.

**Всё описанное выполняется на свой страх и риск.** Разборка и пайка, работа с загрузчиком, NAND и изменениями `/data` могут привести к потере данных или неработающей колонке. Экспериментальное полное восстановление NAND на реальном устройстве автор SpeakerLab не подтвердил. Наличие резервной копии не гарантирует восстановление. Не публикуйте NAND-дампы: они могут содержать ключи, сетевые настройки и другие личные данные.

## Что известно об экземпляре

- Владелец сообщает, что в его L09G установлен **U-Boot от 18.11.2021**. Номер версии и SHA256 фактического кода BL33 для этого экземпляра в сохранённых нами журналах не зафиксированы.
- На этом экземпляре получение root и постоянного SSH получилось с SpeakerLab 1.0, в локальной копии которого была отключена проверка профиля BL33, как описано ниже. Это единичный результат: совпадение даты, названия колонки или прошивки не доказывает совместимость другого устройства.
- Для сравнения: автор статьи исследовал плату AS09A VER0201 с U-Boot 2015.01 от **27.08.2021**. Профиль SpeakerLab относится к тому загрузчику; эта дата не является версией загрузчика колонки владельца данного порта.

## Подготовка и USB

1. Скачайте SpeakerLab 1.0 по ссылке из [статьи на Хабре](https://habr.com/ru/articles/1107780/) и изучите находящиеся в архиве `README_RU.md`, `USB_WIRING_RU.md` и инструкцию для своей ОС. Нужны Python 3.10+, OpenSSH и работающий USB-доступ; в Windows для устройства `1B8E:C003` используется WinUSB. На Windows аппаратный проход также был выполнен в опыте владельца этой L09G.
2. Подготовьте USB 2.0 с передачей данных. При **отключённом** штатном питании и USB подключите к подписанным площадкам платы GND, DP/D+ и DM/D−. USB VBUS/+5 В к плате не подключайте и изолируйте. Проверьте назначение проводов прозвонкой и отсутствие перемычек. Номера контактных площадок на другой ревизии могут отличаться. Колонка питается от штатного блока питания.
3. Подготовьте колонку к подключению к вашей Wi-Fi-сети. На компьютере создайте собственный SSH-ключ (`ssh-keygen -t ed25519 -f speaker-owner-key`); существующий ключ не перезаписывайте. Для установки понадобится только публичный файл `.pub`, приватный ключ остаётся у владельца.
4. Запустите SpeakerLab на компьютере. Для захвата краткого USB-окна сначала выберите операцию и дождитесь сообщения об ожидании USB, **затем полностью выключите и включите штатное питание колонки**. Обычного программного reboot может быть недостаточно.

## Проверка BL33 и отличие случая владельца

В исходном SpeakerLab `speakerlab/transport.py`, метод `TPL.verify_profile()`, читает участки BL33 и сравнивает их SHA256 с `profile.json`. Вызовы выполняются по адресам, изученным на конкретном загрузчике. Автор SpeakerLab **прямо запрещает убирать эту проверку ради похожего загрузчика**. Поэтому штатный способ — оставить проверку включённой и остановиться при несовпадении. Несовпадение — не доказательство, что безопасно продолжать.

Для документации использованного эксперимента: в копии SpeakerLab владельца на его U-Boot от 18.11.2021 три строки проверки были закомментированы, а отметка `self.verified = True` и событие оставлены. Фрагмент выглядел так:

```python
    def verify_profile(self):
        # for segment in PROFILE['code']:
        #     if sha(self.read(segment['address'], segment['size'])) != segment['sha256']:
        #         raise RuntimeError('Unknown stock BL33. Stop: this release supports one measured build only')
        self.verified = True
        self.event('profile_verified', name=PROFILE['name'])
```

**Это отключает проверку совместимости, включая проверку перед чтением NAND и установкой root.** При таком изменении `profile_verified` в журнале и имя профиля в `backup.json` записываются даже без сравнения хешей. Они не подтверждают, что загрузчик соответствует профилю; дата загрузчика владельца известна с его слов, а не из этого события. Самостоятельно сравните исходный код вашей версии SpeakerLab: фрагмент относится к 1.0, в других выпусках он может отличаться. Использование изменённой проверки противоречит рекомендации автора и может вызвать выполнение кода по неверным адресам. Успех на одном устройстве не устраняет риск для другого.

## Резервная копия и SSH

1. В SpeakerLab выберите папку результатов, выполните **три чтения NAND** с OOB и затем **«Проверить копию»**. Для каждого чтения в профиле AS09A указано 285 212 672 байта; сохраняйте все три файла и отчёт, включая предупреждения и расхождения. Проверка подтверждает целостность сохранённых файлов, но не отсутствие ошибок чтения. При отключённой проверке BL33 также нет гарантии, что чтение вообще выполнялось совместимым с устройством кодом.
2. Сохраните копию отдельно от компьютера и убедитесь, что понимаете доступные способы восстановления. В графическом интерфейсе выберите завершённую копию с **этой же** колонки и публичный `.pub` ключ; слот оставьте `auto`. Запустите **«Получить root / SSH»**, дождитесь ожидания USB и только тогда выключите и включите питание.
3. После завершения дождитесь подключения колонки к сети, найдите её IP и проверьте вход и автозапуск:

   ```sh
   ssh -i ./speaker-owner-key root@IP_КОЛОНКИ
   id
   /data/speakerlab/rootctl status
   ```

   Ожидаются `uid=0(root)`, `running=yes` и `autostart=enabled`. Затем обычной перезагрузкой и повторным входом проверьте, что SSH сохраняется. Сообщение о передаче управления ядру само по себе не подтверждает готовность SSH.

SpeakerLab использует overlay в `/data` и не перепрошивает загрузчик и ядро в описанном пути, но запись в `/data` — постоянное изменение. Инструкции по самому порту и возврату его изменений находятся в [README_RU.md](README_RU.md).
